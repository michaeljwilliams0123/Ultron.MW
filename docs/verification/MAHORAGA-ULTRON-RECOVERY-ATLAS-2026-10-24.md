## Recovered prior-conversation failure history (October 19–23)

Earlier Ultron investigations repeatedly found that local green tests were ahead of deployed production state. On October 22–23, the large [Ultron PR #76](https://github.com/michaeljwilliams0123/Ultron.MW/pull/76) cloud brain had **11 of 15** Hatchable files in parity. Four files diverged: `api/brain/run.js`, `api/brain/tick.js`, `lib/brain-owner.js`, and `lib/brain-runner.js`. The completion database exception was also coupled to the objective-failure handler until it was separated, preventing false failure receipts or automatic side-effect replay. Later work moved the backend to version 6 and merged new recovery integration PRs; this **does not retroactively prove** that the current v6 deployment manifest equals current GitHub main, nor that real external writes have succeeded. Use `scripts/verify-hatchable-parity.mjs` and the live Hatchable deployment manifest at every cutover.

An October 20 live GitHub comment-to-patch repair revealed a false negative after creating a PR head: GitHub readback had not converged yet, and an impatient retry would have repeated the write. The repaired pattern used bounded observation without repeating mutations, then verified the complete comment → patch → commit → Verify → reply cycle. That same rule explains why the current `mahoraga_actions` `sent` or `uncertain` entries must only read back outcomes and **never POST twice**. Mahoraga's [PR #806](https://github.com/michaeljwilliams0123/mahoraga/pull/806) documents a related late-browser-response timeout: do not confuse a slow answer with failed cognition and replay.

Owner Chrome acceptance grew from [Ultron #72](https://github.com/michaeljwilliams0123/Ultron.MW/pull/72), [#73](https://github.com/michaeljwilliams0123/Ultron.MW/pull/73), [#74](https://github.com/michaeljwilliams0123/Ultron.MW/pull/74), and [#85](https://github.com/michaeljwilliams0123/Ultron.MW/pull/85): actual Chrome navigation, DOM recheck and one demonstrated write are stronger than mocks, but isolated browser tests still do not authorize external credentials, account sign-in/MFA, multipart transfers or multi-window acceptance. One local finding also exposed a TOCTOU upload hazard: a validated approved file path may change before Playwright reads it; capture/revalidate immutable bytes at execution time rather than trusting a stale filename.

Destiny separation was historically confused with the GitHub Actions bot that published a PR. [Ultron #81](https://github.com/michaeljwilliams0123/Ultron.MW/pull/81) defined routing and [#83](https://github.com/michaeljwilliams0123/Ultron.MW/pull/83)/[#84](https://github.com/michaeljwilliams0123/Ultron.MW/pull/84) tracked claims and receipts; the GitHub author alone cannot prove that a separate Destiny Work session executed a task. Mahoraga's metered workspace routing and verified-decline failover provide templates, but never assign one user's bill or identity to another without a genuine workspace attestation.

The past implementation also showed a productive constraint: reviewable consolidated framework changes, real side-effect receipts, and a single Pages UI improved the architecture, while redundant hosting lanes, repeated status narration and broad no-evidence permission claims caused recurring stalls. Maintain the one UI / one durable backend design and preferentially adapt proven code rather than making another browser, auth or cloud plane.

## Fix in this PR: live-action recovery fairness

**Observed source defect:** `resumePendingMahoragaActions` previously selected `ORDER BY id ASC LIMIT 2`. An old `prepared` canary without credentials or `uncertain` readback without matching receipt could consume both slots every hour and indefinitely starve later actions, even though an always-on scheduler was healthy.

- Add `0005_mahoraga_scan_fairness.sql` with `last_scanned_at` (nullable) and pending-state index, retaining all existing side-effect checkpoints.
- Select the least recently scanned admitted actions; mark every attempted scan, including unavailable credentials and unresolved receipts. The `sent`/ `uncertain` state machine remains readback-only; no new POST or autonomous goal is introduced.
- Regression tests simulate four pending actions with a limit of two across sequential hours, and reject a failed bookkeeping write instead of reporting a false successful scan.

**Release acceptance still separate:** source test green → independent review → exact-head Verify → protected squash merge → stage matching Hatchable migration/source → dry-run deploy → owner decision to deploy → version/manifest readback → verify scheduled operation and fair scans → real scoped issue canary only after credentials → genuine source-of-truth readback. The UI must distinguish each stage.

## Target architecture from the lessons

Single GitHub Pages cockpit → optional Descope identity sign-in → **server-validated owner session** → one durable Hatchable Postgres brain → GitHub App/MCP/browser-specific adapters with independent credentials → typed tasks + leases + no-replay receipts → independent outcome evaluator → code proposal PR with exact-head CI and review. Hourly tick provides durable maintenance, while user-triggered `scheduler.now` handles immediate tasks. Neither mode claims an uninterrupted model process.

An ambitious intelligence roadmap means improving measured capability: actual unseen-task completion, lower intervention, higher prediction calibration, verified recovery, self-identified uncertainty, reproducible learning and cost per correct outcome. Sentience is not implied by introspective language or autonomous operation.
