# PR #85 — Real external file transfer and native window acceptance

## Execution scope (SD009WC7, October 23, 2026)

This is a real system-Chrome browser acceptance run on an isolated Windows
desktop, with a public external echo service. All input file contents
are generated ephemeral test bytes, never user documents or credentials.
Test command (Windows, existing optional Playwright and system Chrome):

```powershell
node scripts/computer-external-transfer-window-acceptance.mjs --synthetic-public
```

The command creates two separate headed Chrome browser contexts (two different
native Chromium window IDs verified via CDP), preallocates a secondary native
window, navigates, switches back and forth, closes the secondary context, and
checks the primary context remains alive. No unsolicited page or window is
added to admitted slots.

**Real external upload:** the browser selects a generated canary file through
the production driver and posts a multipart form to Postman Echo over HTTPS.
The external provider echoes the complete original bytes encoded as Base64.
The script checks an exact match to the independent locally generated bytes
and records only a SHA-256 digest. Postman Echo does not persist uploads; its
response is independent remote readback of transfer, **not durable remote
storage**.

**Real external download:** the browser initiates an HTTP attachment from
httpbin.org, receives the genuine Playwright download event, and persists
the bytes exclusively into an ephemeral approved directory. It parses the
returned JSON, checks Content-Disposition, and independently computes SHA-256
of the on-disk file. No pre-existing file is overwritten.

**Hostile redirect negative acceptance:** a locally hosted synthetic multipart
POST endpoint responds with 302 to a second **non-allowlisted** origin.
The first endpoint sees exactly one request; the second endpoint sees zero.
The network route fetches one response with `maxRedirects:0` and fails
closed. The upload is never retried. This test exposed an important issue
in Playwright: calling `route.continue()` for a file stream followed the
redirect without another allowlist interception, so that option was
removed before PR review.

## Upload data integrity fix

Playwright's `route.fetch()` originally transmitted a multipart form with
an *empty* file field even though Chrome had selected the nonempty file.
Allowing the original browser request via `route.continue()` fixed the
body but left the redirect escape described above. Production now instead
uses a one-use memory-only multipart bridge: after an approved `upload`,
the driver records the canonical regular-file path, filename, input field,
size and SHA-256. Only a separately approved submit `click` arms the bridge,
and that click's explicit `sendToOrigin` property binds the recipient into
the plan fingerprint and local approval preview. Same-origin submit uses
the current page origin by default.

For the **one** bound multipart request, the network layer reads the original
browser part headers, rejects any unexpected filenames/fields/nonempty
placeholders, revalidates the file SHA-256 and canonical approved-root path,
reinserts the exact approved file bytes and uses
`route.fetch({postData, maxRedirects:0})`. The one-time grant is consumed
*before* network dispatch; uncertain outcomes cannot be automatically
replayed. Out-of-root files, disallowed origins, more than one file, stale
files, wrong filename/field, oversized payload, unexpected redirect,
unapproved request and duplicate use fail closed. The browser never stores
file bytes in a checkpoint, GitHub, or logs.

All browser file/window actions remain opt-in in the existing owner runner:
`ULTRON_BROWSER_UPLOAD_ROOT`, `ULTRON_BROWSER_DOWNLOAD_ROOT`,
`ULTRON_BROWSER_MULTITAB=1`, and
`ULTRON_BROWSER_MULTIWINDOW=1` are required for their respective
operations. The existing local per-action randomized approval (not CI or an
LLM) is still required for real upload and submit actions.

## Evidence boundaries

- The *external* Postman / httpbin / native-window test is a **synthetic
  canary harness using real external networking**, with no owner login,
  owner randomized challenge or private account. It is not proof of a
  real-owner-approved file upload to a personal third-party account.
- The separate GitHub browser canary and original durable checkpoint
  already demonstrated owner-authorized browser write plus independent
  application readback and no duplicate dispatch.
- File transfers on an authenticated private third-party service,
  cross-machine windows, provider-account revocation, and production
  hosted/browser operation have **not** been exercised. Maintain those as
  separate follow-up acceptance work in Issue #65 and the owner-provider
  admission track; do not claim them complete or require them for
  *merging opt-in source code*.
- This is an opt-in **source merge**, not permission to deploy a hosting
  service, bypass owner consent, rotate credentials, or promote PR #76.
