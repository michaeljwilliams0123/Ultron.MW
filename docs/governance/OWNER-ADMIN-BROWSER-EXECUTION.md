### What the user blueprint gets right

New remote MCP requests in protocol `2026-07-28` carry self-describing version/client metadata inside `params._meta`. GitHub administration generally requires an identity with the actual provider-supported granular permissions rather than simply expanding the default workflow `GITHUB_TOKEN`. Short-lived installation tokens and fail-closed worker admission are appropriate **after** owner, installation, operation and scope are verified. Real browser login/session state is distinct from MCP transport state. See the [MCP conformance matrix](MCP-CONFORMANCE-MATRIX.md) in PR #350 and official references below.

## 2. Do NOT copy the example workflow or runner verbatim

The pasted blueprint is an **unreviewed proposal**, not an executable production security baseline:

1. **Shell injection** — `npx ts-node ... '${{ github.event.inputs.payload_json }}'` and `--payload='${{ ... }}'` insert attacker-influenced strings into a shell expression. An input containing a single quote can break quoting. Pass the dispatch payload in an environment variable, stdin or a file generated by an isolated step, then parse and validate an exact schema. Do not interpolate request JSON into `run:`.
2. **Signature presence is not authorization** — `if (isHighRiskWrite && !humanApprovalSignature)` checks only non-emptiness, not key ownership, expiry, exact plan, repository, capability, resource, source SHA, profile/stop versions, nonce or replay. Verify the actual existing P-256 owner-signed envelope from a pinned public key **before** minting a provider token or dispatching work. A caller-provided `isHighRiskWrite=false` must never down-classify a privileged operation; policy determines risk from the operation, not task text.
3. **MCP metadata is not a bearer grant** — a JSON-RPC `params._meta.authorizationToken` field is not evidence that the caller is authenticated. A server-issued, appropriately audience-bound credential must be validated at the actual transport/executor boundary. Use server-owned identity and policy checks; neither `clientInfo` nor arbitrary `_meta` confers new permissions.
4. **Regex isn't AST/IR** — the example's blacklist can both reject harmless strings and miss encoded/incrementally constructed attacks. Treat lexical checks as limited defense in depth. Validate URL scheme/host/port, operation IDs, exact parameter keys and sizes, navigation/redirect destination and provider semantics. Track the benchmarked parser/flow project under #349; do not rename regex screening as an AST/IR security proof.
5. **No arbitrary browser origin** — the example accepts an arbitrary `targetUrl`, selector and serialized `PLAYWRIGHT_STORAGE_STATE` from a shared workflow secret, without an operation-scoped origin allowlist, redirect/subresource protections, account identity/consent or lifecycle controls. Existing bounded browser tests are intentionally isolated. A future authenticated SaaS worker must use an owner-approved provider/session binding and an isolated encrypted secret store with expiry, revocation and no cookie/log/artifact disclosure.
6. **Page title is not effect proof** — completion of `locator.click()`, `fill()` and `page.title()` establishes neither a server-side mutation nor its intended actor/count. Return `reconcile-required` when an operation may have been submitted but readback is unknown; do **not** blindly retry. Require independent provider-side GET/readback, stable objective/idempotency key and durable receipt.
7. **Incomplete example code/tests** — proposed `navigate` is not implemented in the runner, the validation function calls `process.exit` rather than throwing a testable error, and mock `Example Domain` DOM acceptance is not authenticated service-write acceptance. The TypeScript/Jest/Zod layout is not the repository's current Node `src/` + `test/` runner convention; do not introduce toolchain churn without a measured benefit.
8. **Privilege/deployment drift** — adding `admin-execution.yml` or `governance-gate.yml` as another privileged dispatcher would duplicate the existing owner P-256 grant, Hatchable ledger and worker routing. The proposed GitHub environment approval is optional hardening if it is truly owner-operated; do not invent a second required human approval or weaken GitHub branch protection. GitHub App installation permissions, repository visibility and provider capabilities must be verified, not presumed. Use SHA-pinned reviewed Actions rather than unpinned `@v1`/`@v4` in sensitive workflows.

## 3. Canonical future admin/browser transaction (one lifecycle)

1. **Owner objective:** Hatchable receives a structured objective, operation ID, exact target repository/provider, expected effect and rollback; records immutable source/policy/profile/stop versions and `$0` paid ceiling.
2. **Admission:** Identify the actual provider App installation and target repo/tenant. Derive allowed risk from the server-side registry (#187/#225); verify owner identity and existing scope-bound single-use P-256 step-up for admin (#169), including nonce/expiry and resource fences. Reject mismatched `_meta`, user labels or Council claims.
3. **Reserve before effect:** Hatchable commits a one-writer, version-fenced outbox/idempotency record. If a duplicate or unknown prior attempt exists, read/reconcile rather than dispatch twice.
4. **Mint and execute least-privilege identity:** Obtain a short-lived downscoped GitHub installation token only for the already approved repository and operation; ordinary test/repair/browser workers remain unprivileged. For third-party browser actions, use a separately authorized isolated session to the exact approved origin, with protected storage, consent/MFA when required, cross-origin egress denial and one bounded action budget. Never put serialized session state in workflow logs or source.
5. **Verify independently:** Read authoritative GitHub/provider state *through a separate trusted readback*; compare exact resource, actor, source SHA, expected before/after, effect count and fee/cost. A DOM/title-only observation remains `dom-verified-only`; an ambiguous submission becomes `reconcile-required`.
6. **Settle/rollback:** Write immutable, redacted outcome evidence to PostgreSQL, propagate only status/receipt identifiers to GitHub and the Hatchable UI. Enforce stop/revoke on new effects; rollback only through a separately authorized bounded operation, not a blind compensating write. No self-granted new permission or paid fallback.

This lifecycle is a **contract** for existing #169, #187, #192, #225, #285 and #204—not an assertion that the complete admin or universal third-party browser flow is currently live.

## 5. Retirement decision

**No retirements authorized.** Retain the existing Hatchable worker, owner P-256 grant machinery, PostgreSQL outbox, local MCP stdio, browser DOM-only tests as *DOM-only*, and separately proved internal Hatchable write canary. Propose retirement only for an actually inventoried duplicate executor after a parity test, owner consent, canary, rollback and verified live postcondition. Any new script or workflow must state why a shared executor cannot support its exact bounded operation first.
